## Camera
- **Upload site:** `glUniformMatrix4fv`, every frame, re-uploaded to each program that needs it (not shared via UBO). Camera and projection are **separate uniforms**, never pre-multiplied on the CPU. **Exception:** some effects (the ship light glows) are transformed into view space **on the CPU** and drawn with only `inMatP` — see group C below.
- **Uniform naming** (from `glGetUniformLocation` at link time): `inMatV`, `inMatC`, `inMatP`, `inMatM`, `inMatMV`, `inMatFL`/`inMatKL` (fill / key light — never touch), plus `vec4 inCamera` (camera world position) in programs 58, 60, 78.
- **Where the camera enters — all 93 programs classified** (vertex shaders read from the trace; note 82 of the 274 `glShaderSource` calls use apitrace's `string = &"..."` form, which an earlier pass missed):

## Engine frame structure (Ghidra, build 12653478)
Addresses are Ghidra's (image base 0x00400000); at runtime add `HomeworldRM.exe base - 0x400000`. Names below are our labels in `re/ghidra/HWRM.gpr`.
- `SwapBuffers` (GDI32 import, IAT slot 0x00868020) is called only from `rnd_SwapNow` 0x0078e1f9 and `rnd_FrameStart_SwapIfPending` 0x0078e20d. The swap is **deferred**: `rnd_FrameEnd_FlushMarkPending` 0x0078df6d (flush render queue `FUN_00795289` → `glFlush` → `swapped = 0` at `DAT_009ae7b8`) ends a frame, and the next frame's start (`rnd_FrameStart_SwapIfPending`, from `game_BeginFrame` 0x005f2aeb) swaps it. `rnd_Clear` 0x0078df2b(mask) clears.
- Gameplay frame: `game_BeginFrame` 0x005f2aeb (per-frame timing/camera globals, swap previous, clear; reached through a function pointer — no static callers) → `game_UpdateAndRenderWorld` 0x00525d4c → `game_EndFrame_UICursor` 0x005f2c00 (UI cursor phases, then `rnd_FrameEnd_FlushMarkPending`, then a callback list). Loading screens present via `rnd_PresentLoadingFrame` 0x0054d676.
- `game_UpdateAndRenderWorld` **mixes state updates with rendering**: it advances animation/effect clocks (`+= dt` on several objects) before rendering, then `PHASE_SceneIn` → `depthInfo` uniform (near/far from the camera vtable +0x20/+0x24) → `FUN_00525332` + `FUN_007b0290(dt, 0x0fffffff)` (scene draw) → `PHASE_SceneOut`, then 2D setup (`FUN_0079b68b(0,1,0,1)` ortho) and `FUN_006ac7d7` (UI). Calling it twice per frame would double-advance those clocks — hence synchronized stereo via **GL-level replay** instead of re-running engine code.
- Render phases (data-driven pass hooks run by `rnd_RunPhase` 0x00795500, ids via `rnd_LookupNamedId` 0x007922da): `SceneIn`, `SceneBackPre`, `SceneBackPost`, `SceneBackSensors`, `SceneSOBPre`, `SceneSOBPreLens`, `SceneSOBPost`, `SceneEffects`, `SceneTrails`, `SceneOut`, `SceneUILayerIn/Out`, `UIPre`, `UIIn`, `UIOut`, `UICursorPre/Post`.

## Synchronized stereo (proxy 0.5.0)
- Headset test 4 feedback: judder/jitter severe with alternating-frame rendering (AFR: one eye per game frame, each eye at half rate and showing a different moment).
- Re-running engine code per eye is unsafe (`game_UpdateAndRenderWorld` advances animation clocks), so the second eye is produced by **GL-level replay**: every GL call that affects rendering is recorded while the game renders the left eye; at `wglSwapBuffers` the left eye is copied out, the frame-start GL state is restored, and the recorded stream is replayed through the camera-aware hooks with the right eye's camera; then both eyes are submitted with the same head pose.
- Function census (apitrace, build 12653478): gameplay frames use **77** GL functions, of which ~20 legacy immediate-mode calls are the Steam overlay drawing inside the real swap (outside the recording window); menus/loading add shader compiles and texture uploads (110 total). No buffer mapping, syncs or mid-frame `glReadPixels`.
- Recorded: GL 1.1 state exports (now hooked), ~50 extension functions (scalar ones via a typed template that stores raw stack words; `glBufferData`/`glBufferSubData`/`glUniform*v`/`glDrawBuffers`/... copy their payload), plus the camera-aware program/matrix/framebuffer/draw hooks. Benign (not needed for a replay): queries, object creation, texture uploads, shader setup. Deletes of buffers/VAOs/textures during a recorded frame are deferred until after the replay. Everything else goes through **counting stubs/thunks**; any count during a frame marks it unreplayable (logged), and the right eye keeps its previous image for that frame.
- HUD during replay: 2D draws and the cursor are skipped (already on the overlay); the 3D overlay in the HUD FBO is re-drawn with the right eye's camera.
- Smoke test: a frame drawing two quads through one streaming buffer (re-uploaded per draw, deleted mid-frame) replayed with a shifted camera reproduces exactly the shifted quads.
- **Test 5** (proxy 0.5.0, synchronized stereo, Quest 2 reported at 144 Hz, IPD 70 mm): "judder is gone, no missing effects, significantly smoother with no lag". Telemetry over 6 min: **26,676 of 26,676 frames replayed (no fallbacks)**; ~60 fps in skirmish, ~120 fps in menus (min 50, avg 70); replay CPU 1.7 ms avg / 2.5 ms max; ~5,200 GL calls and ~380 KB payload per gameplay frame. Each eye now updates at the full game frame rate.

- Panel: an OpenVR overlay (`SetOverlayCurvature`, curvature = width / (2π·radius)) fixed relative to the recentre pose, default 1.8 m away, 65° wide curved round the player. Moved/resized/curved with a Factorio-style grab bar (hold the trigger on it; sticks push/pull, size, curve); placement saved in `hw2vr_panel.ini`. Its texture is a filtered copy of the 2D UI (mipmaps + 2×2 taps one level above the output size) at ~20 px/degree, because SteamVR samples overlays without mipmaps.
- Laser (right hand, `/pose/tip`): own ray/plane/cylinder maths (`input/panel_geometry.h`). **The panel is mostly see-through**, so it only counts as UI where a coarse coverage mask of the UI (1/8-size mip level, read back asynchronously one frame late) is set; elsewhere the laser points into the world: mouse = the game projection of the laser direction in the game camera's frame (`input/laser_math.h`), clamped 2% inside the window. A held button keeps the mode it started in. The game's cursor is redirected into its own 128×128 texture centred on the hotspot and shown on the panel, or (world mode) floating `cursor_distance` m out along the ray the game picks along.
- Controller input: SteamVR Input actions (`bindings/`, Steam Frame default binding, grips unbound); injected with `SendInput` (buttons, wheel, keys, relative motion) and `SetCursorPos` (absolute), only while the game window is in the foreground. Left stick orbit = right button held + relative motion (see the relative mode above).

## Headset test 6 and laser depth (proxy 0.7.0)
- **Test 6** (proxy 0.6.0, 2026-10-15, ~2.5 min in VR, 53-74 fps): curved 65° panel "not readable, far too low resolution"; clicking worked "although the buttons are small"; left-hand buttons "odd" (D-pad down looked like the move command - most likely the camera-pan pivot of the arrow keys, unconfirmed: presses weren't logged); and "the cursor being on a single plane that never seems to be touching the ships is really odd". Brendo: shelve the Factorio-style panel; depth first.
  - Readability is a pixels-per-degree problem: the game draws its UI for a 3440 px monitor; squeezing that into 65° at the headset's ~20 px/degree leaves ~0.38 of the pixels. The aligned layout (UI spanning the game's own 118° view) keeps ~0.69.
  - Log: the windowed game's client area was at (8, 31), so its bottom 25 rows were below the monitor (out of the cursor's reach) -> `[vr] fit_window` moves the window while VR runs.
- Scene depth (apitrace, startup calls 20929-20944): **fbo 1 = 16x MSAA, colour `GL_RGBA8` renderbuffer 1 + `GL_DEPTH_COMPONENT32` renderbuffer 2, 3440x1440.** Fbos 2-6 share depth texture 185; the game resolves fbo 1's depth into it with depth blits several times a frame (soft particles / glows).
- **Laser depth probe** (`src/stereo/depth_probe`): after the game renders the left eye (before the second-eye replay), fbo 1's depth is blit-resolved into our own texture of the same format, and a 1x1 fragment shader marches the hand's laser ray (game view space, game units) through it: 192 log-spaced steps from 1 to 400000 units, hit = point behind the visible surface by at most 25% of its depth (so rays passing behind a ship don't count), then 14 bisection steps. Eye-space depth from window depth via the eye projection's depth row (`P[14] / (ndc_z + P[10])`, the game's infinite far plane). Result read back through a fenced pixel-pack buffer, never stalling (usually available the next frame). Smoke test: a 4x MSAA DEPTH32 scene with a quad at 200 units gives 200.00 / 206.16 / 100.00 for straight, angled and offset-origin rays, misses past the edge and from behind.
- Laser into the world: touch point H (game view space) -> mouse = game projection of H, cursor drawn at H (seated space), beam ends there. No touch: mouse along the laser's direction, cursor at the last touch's depth.

## UI phases and world markers (build 12653478, proxy 0.8.0)
- **Test 7** (proxy 0.7.0, 2026-10-15): laser depth worked, but "the 'UI' level is still far away from the actual ship ... the green circle looks like it's floating in space not surrounding the ship"; the right trigger needed "a strong press" for any action; the screen UI should not be "a layer in front of the person". Brendo chose a **console below the view** for the screen UI.
- HUD pass of a gameplay frame (fbo 35, `re/traces/frame_215000.txt` + decoded vertex blobs): after the 3D overlay (prog 70) come the **world-space 2D markers** - selection bracket (prog 54 lines, 40-byte vertices, drawn 5x with `inOfs` pixel offsets for a drop shadow), health bar (prog 54 triangles), ship name (prog 4 text, font texture 904, no scissor), the selection ring (prog 68: a CPU-projected 3D circle, 66 vertices) - then the **screen-space widgets** (prog 8/5/6 with 104-byte vertices, scissored text by prog 4). All positions are CPU-projected into the ortho [0,1] screen space with z = 1 (lines) or 0 (text); vertex attribute 0 = `inPos`.
- Line shaders (prog 54/68): `tryV = inMatP*pos; tryV.xy += inOfs.xy*2*inWindow.zw*tryV.w` - pixel offsets scale with w, so they survive a perspective inMatP unchanged.
- **The engine separates the two**: the UI renderer `FUN_006e527f` sets the [0,1] ortho, runs `PHASE_UIPre`, draws the UI layers flagged world-space (layer +4 == 1), then `FUN_0071619d` runs **`PHASE_UIIn`** (`push [0x00a8eef8]; call rnd_RunPhase` at **0x007161FA**), then the screen-space layers (flag 0), then `PHASE_UIOut` (`FUN_00716212`). `FUN_006ac7d7` (the game-UI layer loop) is reached from there.
- **UI phase hook** (`src/proxy/engine_hooks`): at the first swap the proxy finds that call by signature (the `"PHASE_UIIn"` string -> `push imm32` of it -> `mov [id], eax` -> `push dword ptr [id]; call rel32`) and redirects its rel32 to a naked stub (`mov byte [flag], 1; jmp rnd_RunPhase`). In memory only; nothing patched if any step doesn't match. Smoke test: the finder, run on the real HomeworldRM.exe mapped as an image, returns RVA 0x3161FA (Ghidra 0x007161FA).
- **World markers at depth**: 2D draws into the HUD framebuffer before `PHASE_UIIn` are world markers. Their screen rectangle comes from shadow copies of the small streamed vertex buffers (`src/hud/marker_geometry`: VAO attribute-0 pointers, element buffers, BufferData/SubData tracked); their depth from the **marker grid** (`src/stereo/depth_probe`: one game-camera ray per 20-pixel cell, marched through the resolved left-eye depth, read back a frame late) - nearest surface in the rectangle's middle half, else in the whole rectangle, else the previous marker's depth (a health bar or name next to its bracket). The draw then goes into the HUD layer with `inMatP' = P_eye * E * plane(depth) * P_ortho` (`stereo::place_at_depth`), so each eye sees the marker on the plane at its ship's depth, at the place and size the game camera sees it. Classifications and depths are kept in draw order so the second-eye replay repeats them. Smoke test: markers over / round a quad at view depth 200 anchor at 200.00; the screen widget after the phase still goes to the overlay.
- Screen widgets after `PHASE_UIIn` go to the **console**: a curved panel 0.85 m ahead, 0.42 m below eye level, 80 degrees wide, tilted to face the eye, on a dark backing (premultiplied, opacity 0.6); solid for the laser; grab bar above it. In-game HUD scale (Options > UI, up to 2.5x per area, `ui\newui\optionstabs\ot_ui.lua`) is the readability lever.
