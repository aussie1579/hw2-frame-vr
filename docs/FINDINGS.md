## Camera
- **Upload site:** `glUniformMatrix4fv`, every frame, re-uploaded to each program that needs it (not shared via UBO). Camera and projection are **separate uniforms**, never pre-multiplied on the CPU. **Exception:** some effects (the ship light glows) are transformed into view space **on the CPU** and drawn with only `inMatP` — see group C below.
- **Uniform naming** (from `glGetUniformLocation` at link time): `inMatV`, `inMatC`, `inMatP`, `inMatM`, `inMatMV`, `inMatFL`/`inMatKL` (fill / key light — never touch), plus `vec4 inCamera` (camera world position) in programs 58, 60, 78.
- **Where the camera enters — all 93 programs classified** (vertex shaders read from the trace; note 82 of the 274 `glShaderSource` calls use apitrace's `string = &"..."` form, which an earlier pass missed):

## Engine frame structure (Ghidra, build 12653478)
Addresses are Ghidra's (image base 0x00400000); at runtime add `HomeworldRM.exe base - 0x400000`. Names below are our labels in `re/ghidra/HWRM.gpr`.
- `SwapBuffers` (GDI32 import, IAT slot 0x00868020) is called only from `rnd_SwapNow` 0x0078e1f9 and `rnd_FrameStart_SwapIfPending` 0x0078e20d. The swap is **deferred**: `rnd_FrameEnd_FlushMarkPending` 0x0078df6d (flush render queue `FUN_00795289` → `glFlush` → `swapped = 0` at `DAT_009ae7b8`) ends a frame, and the next frame's start (`rnd_FrameStart_SwapIfPending`, from `game_BeginFrame` 0x005f2aeb) swaps it. `rnd_Clear` 0x0078df2b(mask) clears.
- Gameplay frame: `game_BeginFrame` 0x005f2aeb (per-frame timing/camera globals, swap previous, clear; reached through a function pointer — no static callers) → `game_UpdateAndRenderWorld` 0x00525d4c → `game_EndFrame_UICursor` 0x005f2c00 (UI cursor phases, then `rnd_FrameEnd_FlushMarkPending`, then a callback list). Loading screens present via `rnd_PresentLoadingFrame` 0x0054d676.
- `game_UpdateAndRenderWorld` **mixes state updates with rendering**: it advances animation/effect clocks (`+= dt` on several objects) before rendering, then `PHASE_SceneIn` → `depthInfo` uniform (near/far from the camera vtable +0x20/+0x24) → `FUN_00525332` + `FUN_007b0290(dt, 0x0fffffff)` (scene draw) → `PHASE_SceneOut`, then 2D setup (`FUN_0079b68b(0,1,0,1)` ortho) and `FUN_006ac7d7` (UI). Calling it twice per frame would double-advance those clocks — hence synchronized stereo via **GL-level replay** instead of re-running engine code.
- Render phases (data-driven pass hooks run by `rnd_RunPhase` 0x00795500, ids via `rnd_LookupNamedId` 0x007922da): `SceneIn`, `SceneBackPre`, `SceneBackPost`, `SceneBackSensors`, `SceneSOBPre`, `SceneSOBPreLens`, `SceneSOBPost`, `SceneEffects`, `SceneTrails`, `SceneOut`, `SceneUILayerIn/Out`, `UIPre`, `UIIn`, `UIOut`, `UICursorPre/Post`.

## Synchronized stereo (proxy 0.5.0)
- Headset test 4 feedback: judder/jitter severe with alternating-frame rendering (AFR: one eye per game frame, each eye at half rate and showing a different moment).
- Re-running engine code per eye is unsafe (`game_UpdateAndRenderWorld` advances animation clocks), so the second eye is produced by **GL-level replay**: every GL call that affects rendering is recorded while the game renders the left eye; at `wglSwapBuffers` the left eye is copied out, the frame-start GL state is restored, and the recorded stream is replayed through the camera-aware hooks with the right eye's camera; then both eyes are submitted with the same head pose.
- Function census (apitrace, build 12653478): gameplay frames use **77** GL functions, of which ~20 legacy immediate-mode calls are the Steam overlay drawing inside the real swap (outside the recording window); menus/loading add shader compiles and texture uploads (110 total). No buffer mapping, syncs or mid-frame `glReadPixels`.
- Recorded: GL 1.1 state exports (now hooked), ~50 extension functions (scalar ones via a typed template that stores raw stack words; `glBufferData`/`glBufferSubData`/`glUniform*v`/`glDrawBuffers`/... copy their payload), plus the camera-aware program/matrix/framebuffer/draw hooks. Benign (not needed for a replay): queries, object creation, texture uploads, shader setup. Deletes of buffers/VAOs/textures during a recorded frame are deferred until after the replay. Everything else goes through **counting stubs/thunks**; any count during a frame marks it unreplayable (logged), and the right eye keeps its previous image for that frame.
- HUD during replay: 2D draws and the cursor are skipped (already on the overlay); the 3D overlay in the HUD FBO is re-drawn with the right eye's camera.
- Smoke test: a frame drawing two quads through one streaming buffer (re-uploaded per draw, deleted mid-frame) replayed with a shifted camera reproduces exactly the shifted quads.
- **Test 5** (proxy 0.5.0, synchronized stereo, Quest 2 reported at 144 Hz, IPD 70 mm): "judder is gone, no missing effects, significantly smoother with no lag". Telemetry over 6 min: **26,676 of 26,676 frames replayed (no fallbacks)**; ~60 fps in skirmish, ~120 fps in menus (min 50, avg 70); replay CPU 1.7 ms avg / 2.5 ms max; ~5,200 GL calls and ~380 KB payload per gameplay frame. Each eye now updates at the full game frame rate.

## Marker jitter and motion blur with the turning camera (proxy 0.12.2)
- Brendo (2026-10-19, 0.12.1): health bars still "jittering"; "these were ultra stable before with the old camera system". The 0.12.1 depth memory held back only 0-82 depth jumps per 5 s out of 2,000-3,000 markers - depth wasn't it.
- Flat tests (`[debug] hud_capture = 1`, `camera_turn_test`): **no frame lag** - with the camera turn flipping +-10 degrees every frame the bracket and health bar stay on their ship, so the game places markers with the current frame's camera. But the game **snaps marker positions to whole pixels**: in a 0.02 degree/frame sweep the first marker's bounds moved in exact 1-pixel steps (x 1746.000, 1745.000, ...). With the old fixed camera the markers only moved when ships did; with a camera that follows every head micro-movement they step a pixel back and forth against their smoothly compensated ships -> shimmer. Fix: the game camera holds still until the gaze has moved `[vr] game_camera_deadzone` (3) degrees from its axis, then catches up (`game_fov = auto` adds the dead zone).
- **Camera motion blur** (program 51, post_complex): `outInvC = inverse(inMatCP * inMatC)`, `pastPos = inMatLCP * inMatLC * worldPos`, smear along the difference. With the camera turning with the head, every head movement looked like a camera swing - the +-10 degree test smeared the whole scene sideways - and in VR `inMatC` carries the eye camera while `inMatLC` is the game's raw previous camera, so the vectors were wrong even when still. Fix (GL level, no engine hook): while the camera is overridden, just before program 51 draws, inMatLC := the inMatC the driver got (eye included) and inMatLCP := inMatCP -> zero motion, the pass copies the picture through. Verified flat: the +-10 degree flip test is now crisp.
